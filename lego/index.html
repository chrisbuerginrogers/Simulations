Simulation Hardware

Get both worlds running before you train anything

Simulation and hardware are separate installs with separate failure modes. Prove each one works on its own — the smoke tests in steps 4 and 5 are the ones that matter, because a policy that fails later is almost never failing for the reason you think.

    Python version pin. mjlab and the LEGO library want different things often enough that it is worth keeping them in one environment only if uv sync resolves cleanly. If it fights you, split them: mjlab in this repo's .venv for training, a small separate env for the hardware bridge. The two never need to run in the same process — they exchange a policy file.

    Six projects where RL actually earns its keep

    Each of these fails to have a clean analytical controller, so reinforcement learning is the honest tool rather than a heavier substitute for a PID loop. They are ordered roughly by build difficulty, and each one is chosen to break in a different way when you move it to hardware. Start with the first one.

    Reset burden is the constraint nobody plans for. You will run far more hardware rollouts than you expect while measuring the gap. A task that resets itself (the pendulum falls back to hanging; the fallen robot is already on the floor) lets one student collect fifty trials in an afternoon. A task needing someone to reposition a block every fifteen seconds does not. Weight this at least as heavily as the interesting-ness of the task.
    Check your sensing before committing to a project. SimpleLE's documented surface is motors, colour sensor and controller — orientation and per-motor encoder angles are not part of it. Anything above that wants a heading signal (fall recovery, parking) needs either a gyro exposed through legoeducation directly, or a substitute: dead-reckoned heading from left/right travel, a taped line read with colorSensor.reflection(), or an overhead phone camera. Confirm you can read the signal before designing a task around it.

    Getting an MJCF file that describes your robot

    MuJoCo needs an MJCF — an XML file listing bodies, joints, masses and collision shapes. Nothing LEGO gives you is that file. Three routes get you there, and they trade automation against how much junk you have to clean up afterwards.

    Route A in full — Onshape → MJCF

    The onshape-to-robot exporter reads a top-level Onshape assembly over the API and writes MuJoCo XML directly. This is the route to teach if students are already doing CAD.

    1. Install the exporter and get Onshape API keys from dev-portal.onshape.com.

    pip install onshape-to-robot

export ONSHAPE_ACCESS_KEY=your_access_key
export ONSHAPE_SECRET_KEY=your_secret_key

    2. Structure the assembly so the exporter can read it. This is the part that decides whether the export is usable:

    • It must be a top-level assembly; each instance in it becomes one link.
    • The first instance is the base link — put the chassis first.
    • Mates decide joints: a revolute or cylindrical mate becomes a hinge, a slider becomes a prismatic joint, a fastened mate becomes a fixed joint.
    • Anything you want rigidly joined should be a fastened mate or a sub-assembly, or you will get a model with far more degrees of freedom than your robot has.

    3. Write config.json in the robot's folder. The joint_properties block is where you make the motors behave like LEGO motors rather than ideal ones:

    {
  "document_id": "paste from your Onshape URL",
  "output_format": "mujoco",
  "output_filename": "robot",

  // LEGO motors are weak and springy. Guessing these is the single
  // biggest source of a policy that works in sim and not on carpet.
  "joint_properties": {
    "motor_.*": {
      "actuated": true,
      "forcerange": [-0.25, 0.25],
      "damping": 0.02
    }
  },
  "geom_properties": {
    ".*": { "friction": [0.9, 0.005, 0.0001] }
  }
}

    4. Run the export. You get robot.xml (the model, with Onshape frames exported as site tags you can reference in rewards) and scene.xml (a floor and lighting for a quick look).

    onshape-to-robot robots/my_lego_bot
python -m mujoco.viewer --mjcf robots/my_lego_bot/scene.xml
    Worked if The viewer opens, the robot does not explode or sink through the floor, and dragging a joint moves exactly the parts you expect.
    Whatever route you take, the export is a starting point, not a model. Three things are always wrong on arrival, and all three matter more than the geometry:
    • Collision geometry. CAD meshes carry every stud and pin hole. Replace collision geoms with boxes, capsules and cylinders — keep the mesh for visuals only. This is usually a 10–100× speedup and it is not optional at 2048 parallel environments.
    • Mass and inertia. Onshape only knows masses if you assigned real materials; LDraw-derived meshes never do. Weigh the actual robot on a kitchen scale and distribute it.
    • Actuators. An exported joint is ideal and infinitely strong. Add a real forcerange from a stall test, plus damping and armature, before you believe anything the simulation tells you.

    Train, with the hardware's limits baked in from the start

    The settings that decide whether a policy transfers are not the PPO hyperparameters — they are the control rate, the action delay, and the randomization ranges. Set those to what your hardware can actually deliver, then tune learning second. These are the handful of knobs worth touching first; Task Anatomy has the full list and where each one lives.

    20 Hz is a hardware ceiling, not a preference. Nothing is stored on the hub — every sample has to stream to the PC at the rate your code asks for, and Bluetooth LE tops out around 50 ms per update. Train above the rate you can actually hold and the policy learns to depend on reactions the real robot will never make in time.
